# API-тесты TestBoard

Проект основан на учебном шаблоне Avito `api-tests-student` и использует архитектуру **Client Layer → Manager Layer → Scenario**.

## Источники сценариев

В автоматизацию перенесены только проверки из материалов Avito:
- ТЗ «фронт и бэк для QA»;
- чек-лист ЛР2;
- практические материалы по TestBoard/API;
- текущее задание по автоматизации;
- Swagger TestBoard для контрактов ручек.

## Настройка

1. Склонируйте fork и перейдите в папку проекта.
2. Установите зависимости:

```bash
go mod tidy
```

3. Создайте `.env.override`:

```env
TEST_LOGIN=your_login
TEST_PASSWORD=your_password
```

4. Запуск всех тестов:

```bash
go test -v ./...
```

5. Проверка повторяемости:

```bash
go test -count=3 ./...
```

6. Линтер:

```bash
golangci-lint run
```

## Часть 1. Добавление объявления

Основной позитивный сценарий из задания:
- создание объявления со всеми параметрами;
- получение созданного объявления;
- поиск по полному названию;
- получение фотографий через `GET /advertisements/{id}/photos`.

Дополнительно автоматизированы API-проверки из ЛР2 и ТЗ:
- title длиной 50 символов;
- description длиной 500 символов;
- цена 0;
- отсутствие необязательной цены;
- quantity = 100;
- объявление с 1 фотографией;
- объявление с 3 фотографиями.

Негативные сценарии:
- отсутствующий title;
- пустой title;
- title длиной 51 символ;
- отсутствующее description;
- description только из пробелов;
- description длиной 501 символ;
- отрицательная цена;
- цена больше 1 000 000;
- quantity = 101;
- отсутствие обязательной фотографии;
- отсутствующий токен;
- неверный токен.

Кейс «выбрано 4 фотографии — в форму добавляется не более 3» не перенесён как отдельный негативный API-тест: в ЛР2 это проверка поведения интерфейса при выборе файлов, а не заданный контракт ошибки API.

## Часть 2. Избранное

Автоматизированы только сценарии из текущего задания:
- добавление объявления в избранное и наличие в `GET /favorites`;
- удаление объявления из избранного;
- исчезновение из избранного после удаления самого объявления;
- добавление и удаление несуществующего `ad_id`;
- запросы без авторизации — HTTP 401;
- повторное добавление одного объявления;
- попытка добавить собственное объявление.

Для бизнес-ограничений, где в тексте задания не приведён конкретный HTTP-код или буквальный текст ошибки, тесты не придумывают их: проверяется структурированная клиентская ошибка 4xx с непустым сообщением. Для 401 используется точный код, явно указанный в задании.

## Изоляция тестов

Тесты сами создают необходимые объявления и очищают их через `t.Cleanup`.

Для сценариев избранного нужен второй пользователь, потому что своё объявление добавлять в избранное нельзя, а сценарий удаления самого объявления требует владельца и другого пользователя. Тестовый пользователь создаётся через регистрацию TestBoard и переиспользуется при повторных запусках.

Сценарии не зависят от заранее созданных объявлений в аккаунте и рассчитаны на последовательные повторные запуски.
